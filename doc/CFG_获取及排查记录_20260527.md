## 代码追溯：从 `tof-net-collect` 获取 CFG 的路径

### 1) `tof-net-collect` 主流程先导出本机模块 CFG
`examples/tof-net-collect/src/main.cpp` 里的 `CameraRawSource::export_module_cfg()` 会尝试多个输出路径，然后调用：

```cpp
auto st = camera_->setControl("saveModuleCFG", path);
```

如果控制调用成功且文件真的被创建，就读取该文件并作为 `ModuleCfg` 返回；随后在 `session()` 中把它打包成 `MessageType::CfgFile` 发给 B 端。

### 2) 网络协议里 CFG 是独立消息类型
`examples/tof-net-common/include/tof_net/protocol.hpp` 里定义了：

- `MessageType::CfgFile = 9`
- `CfgFilePayloadHeader { cfg_bytes, filename }`

说明 `tof-net-collect` 发送的 CFG 不是混在 RAW 里，而是作为单独控制/校准消息发给网络 viewer。

### 3) SDK 入口把 `saveModuleCFG` 直接转到 `saveCFGToFile()`
在 `sdk/src/cameras/itof-camera/camera_itof.cpp`：

```cpp
} else if (control == "saveModuleCFG") {
  return saveCFGToFile(value);
}
```

因此，`tof-net-collect` 能否拿到 CFG，本质上取决于 SDK 里 `saveCFGToFile()` 前面有没有成功填充 `m_tempFiles.cfgFile`。

### 4) `saveCFGToFile()` 只复制临时文件，不会自己读 EEPROM
同一文件中：

```cpp
if (m_tempFiles.cfgFile.empty()) {
  LOG(ERROR) << "CFG files is unavailable. Perhaps CFG content was not read from module.";
  return aditof::Status::UNAVAILABLE;
}
```

也就是说，`saveModuleCFG` 不会主动重新读取模块内存；它只是把已经在 `loadModuleData()` 中解析出来的临时 CFG 文件拷贝到目标路径。

### 5) 关键短路点在 `loadModuleData()`
`camera_itof.cpp` 里：

```cpp
if (m_adsd3500Enabled) {
  return status;
}
```

这会让 ADSD3500 路径直接跳过 `ModuleMemory::readModuleData()`，因此 `m_tempFiles.cfgFile` 没机会被写入。

### 6) `ModuleMemory::readModuleData()` 本身是支持 CFG 的
`sdk/src/cameras/itof-camera/module_memory.cpp` 明确有：

```cpp
case CHUNK_TYPE_CFG:
case CHUNK_TYPE_IMAGER_FIRMWARE_FACTORY_HEADER:
  LOG(INFO) << "Found module memory CFG chunk, parsing...";
  cfgFilename = writeTempCFG(pChunkData, payloadSize);
```

这说明问题不在 CFG 解析能力本身，而在 ADSD3500 分支没有走到解析步骤。

### 7) 代码结论
`tof-net-collect` 的 CFG 获取链路是：

`session()` -> `export_module_cfg()` -> `camera_->setControl("saveModuleCFG", path)` -> `CameraItof::saveCFGToFile()`

而在 ADSD3500 下，`loadModuleData()` 被短路，导致 `saveModuleCFG` 没有可复制的临时 CFG 文件，所以最终导出失败。

## 可能的替代获取 CFG 的方法（按优先级排序）

1. 从 SD 卡 / 镜像中提取 CFG
- 设备启动日志里显示 SD 卡镜像版本（例如 `microsd-4.2.0-*.img`），镜像里可能包含设备固件或默认 CFG 文件。
- 操作思路：挂载 SD 卡分区或在镜像上挂载，搜索常见目录（`/etc`, `/opt`, `/root`, `ToF/config`, `config/` 等）以及 `*.cfg` 文件。

命令示例：
```bash
# 在主机上挂载设备插入的 SD 卡（示例设备路径，请按实际调整）
sudo mount /dev/mmcblk0p1 /mnt || true
find /mnt -type f -iname "*.cfg" -o -iname "*cfg*" | head -n 50
# 若是镜像文件：
sudo mkdir -p /mnt/img
sudo mount -o loop,ro microsd-4.2.0-b260ad46.img /mnt/img || true
find /mnt/img -type f -iname "*.cfg" -o -iname "*cfg*" | head -n 50
```

2. 从 U-Boot / 根文件系统读取（如果摄像头内的存储以 Mass Storage 方式暴露）
- 摄像头在 USB 上有 Mass Storage 接口（`lsusb -t` 中可见），拔插后可能以可挂载磁盘出现。
- 尝试识别并挂载该块设备，搜索 CFG 与 config 文件。

命令示例：
```bash
# 查看新的块设备
dmesg | tail -n 50
lsblk
# 假设设备为 /dev/sdb1
sudo mount /dev/sdb1 /mnt/cam || true
find /mnt/cam -type f -iname "*.cfg" -o -iname "config*" | head -n 50
```

3. 通过 SDK 的其他导出接口（如果 `saveModuleCFG` 失败，尝试 `saveModuleCCB` / 导出 module dump）
- `CFG问题排查20260525.md` 提到 CCB 可以导出。导出 CCB 后，查看 CCB 是否包含对 CFG 的指针或能帮助重建 CFG。
- 尝试调用 `camera->setControl("saveModuleCCB", path)` 或使用 `tof-net-collect` 的导出流程抓取 CCB 文件。

4. 从采集端（A）或工程端/同事处索要 CFG
- 如果摄像头出厂或测试时曾生成 CFG，向生产/测试人员或相同固件版本的设备请求导出 CFG，直接复用。

5. 从固件 / 发布仓库 / SDK 配置分支查找默认 CFG
- 在 `ToF` 仓库内搜索 `config/*.cfg`, `config/*.ini`, `RawToDepth*.ini` 等，或者查找固件 release 包中可能包含的 CFG 起始模板。

命令示例：
```bash
# 在工作区搜索
grep -R --line-number "CFG" ToF || true
grep -R --line-number "RawToDepth" ToF || true
```

6. 通过网络端（B 端）与 A 端协作
- 如果网络流中曾发送过 CFG，检查网络接收端保存目录（`tof-net-collect` / `tof-net-viewer` 日志或数据文件）是否已接收并保存过 CFG 文件。
- 在 B 端的接收目录或历史记录中查找 `*.cfg`。

7. 重建 CFG（最不优先）
- 若知道相机固件版本、mode/ini/ccb，可以尝试基于 `RawToDepth` ini 与固定参数重建一个足够用的 CFG，但风险较高且需验证结果质量。

## 推荐的下一步（短期优先）
1. 检查摄像头作为 Mass Storage 暴露的分区，尝试挂载并搜寻 CFG（方法 2）。
2. 在主机上挂载或检查 SD 镜像（方法 1）。
3. 从 `tof-net-collect` 或 `tof-net-viewer` 的运行目录和日志中查找是否曾保存过 CFG（方法 6）。
