# ADSD3500 CFG 获取实施草案（2026-05-27）

## 背景
- 当前 `tof-net-collect` 走的是 `saveModuleCFG -> saveCFGToFile()` 链路。
- 在 `sdk/src/cameras/itof-camera/camera_itof.cpp` 中，`m_adsd3500Enabled` 时 `loadModuleData()` 直接返回，导致 `m_tempFiles.cfgFile` 为空。
- `saveModuleCCB` 已有 ADSD3500 专用实现 `readAdsd3500CCB()`，说明 CFG 也可以按同样思路补一条专用读取链。

## 目标
- 让 ADSD3500 路径也能导出模块 CFG。
- 让 `tof-net-collect` 能拿到有效 CFG 并发送给网络端。
- 尽量不影响非 ADSD3500 的既有模块读取逻辑。

## 推荐方案
优先采用“新增 ADSD3500 专用 CFG 读取函数”的方式，而不是改 `saveCFGToFile()` 的语义。

原因：
- `saveCFGToFile()` 目前是纯拷贝临时文件，职责清晰。
- 读取模块数据与导出文件分离，便于排查。
- 可直接复用 `readAdsd3500CCB()` 的调用方式和错误处理风格。

## 实施步骤

### 1) 新增 `readAdsd3500CFG()`
- 在 `camera_itof.cpp` 中新增一个与 `readAdsd3500CCB()` 风格一致的函数。
- 读取流程尽量参照 CCB 逻辑：
  - 发送读取命令
  - 读取 header
  - 计算总长度和 chunk 数
  - 分块读取 payload
  - 退出 burst/切回 standard mode
  - 校验 CRC
  - 写入临时文件
  - 赋值给 `m_tempFiles.cfgFile`

### 2) 在 `setControl("saveModuleCFG")` 中补 ADSD3500 分支
- 参考现有 `saveModuleCCB`：

```cpp
} else if (control == "saveModuleCFG") {
    if (m_adsd3500Enabled) {
        status = readAdsd3500CFG();
        if (status != Status::OK) {
            LOG(ERROR) << "Failed to load cfg from adsd3500 module!";
            return Status::GENERIC_ERROR;
        }
    }
    return saveCFGToFile(value);
}
```

  ### 2.1) 本次已落地的代码
  - `CameraItof::setControl("saveModuleCFG")` 已在 ADSD3500 分支前增加 `readAdsd3500CFG()`。
  - `CameraItof::readAdsd3500CFG()` 目前作为保守刷新入口，实际通过 `loadModuleData()` 重新填充临时 CFG。
  - `loadModuleData()` 已移除 ADSD3500 早退，允许在模块内存可访问时继续解析 CFG chunk。

### 3) 统一临时文件命名
- 建议临时文件名使用 `temp_cfg.cfg` 或带 PID 的独立文件名。
- 避免与 CCB / JSON 临时文件互相覆盖。

### 4) 补充日志
- 成功：打印读取字节数、CRC 是否有效、临时文件路径。
- 失败：区分命令失败、读取失败、CRC 失败、切模式失败。

## 需要确认的关键点

### 1) CFG 对应的 ADSD3500 读取命令
- `readAdsd3500CCB()` 里命令码是 `0x13`。
- CFG 是否有单独命令码需要确认；如果没有，就要看是否与 CCB 走同一 payload 命令但不同内容头。

### 2) CFG 的 header 格式
- 需要确认 CFG 返回数据的：
  - 头部长度
  - chunkSize 编码
  - 总文件大小字段位置
  - CRC 位置与算法

### 3) 是否和 CCB 一样需要切回标准模式
- CCB 读取完成后需要写回 `switchBuf`。
- CFG 若走同一设备态，也应同步处理。

### 4) 是否存在 EEPROM 里没有 CFG 的情况
- 若模块 EEPROM 里压根没有 CFG chunk，新增函数也只会失败。
- 这种情况要保留网络端 fallback 或外部配置兜底。

## 验证步骤

### 单元级检查
- 编译 `sdk` 和 `tof-net-collect`。
- 确认 `saveModuleCFG` 在 ADSD3500 下不会立刻返回 UNAVAILABLE。

### 联调检查
1. 启动 A 端 `tof-net-collect`。
2. 观察是否打印：
   - `Exported current module CFG: ...`
   - `sent current module CFG to Machine B: ...`
3. 启动 B 端 viewer，确认日志里收到并保存 CFG。

### 回归检查
- 非 ADSD3500 设备继续走 `loadModuleData()` 旧路径。
- 现有 CCB 导出不受影响。
- 网络 viewer 在收到 CCB + CFG 后仍能正常初始化 TOFI。

## 风险与回退

### 风险
- CFG 读取命令或格式不一致，导致读出来的文件无效。
- ADSD3500 设备态切换错误，影响后续通信。
- 临时文件管理不当造成覆盖或残留。

### 回退
- 若新函数不稳定，先保留原逻辑，仅在可控设备上启用。
- 通过配置开关或编译宏临时关闭 ADSD3500 CFG 导出。

## 建议的下一版改动顺序
1. 先把 `readAdsd3500CCB()` 抽象成可复用模板。
2. 基于模板实现 `readAdsd3500CFG()`。
3. 接入 `saveModuleCFG` 分支。
4. 用 `tof-net-collect` 和 `tof-net-viewer` 跑一轮端到端验证。

## 备注
- 本草案只描述实施方向，不包含最终协议命令码和具体 CRC 参数；这些需要结合设备实际返回数据再定。
- 当前实现采用保守方案：优先恢复模块内存 CFG 导出链路，未引入新的 ADSD3500 专用 CFG payload opcode。
